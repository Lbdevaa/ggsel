# Состязательные сценарии

Каждый сценарий реализован в `scripts/race.mjs` и печатает строку «сценарий → ожидание → факт → OK/FAIL». Таблица заполняется по мере реализации этапов.

| # | Сценарий | Ожидание | Этап | Статус |
|---|---|---|---|---|
| R1 | 50 параллельных вебхуков `paid` с разными `event_id` по одному заказу | 1 выдача, 1 ключ списан у поставщика | 2 | PASS |
| R2 | 20 повторов одного `event_id` | состояние заказа не меняется | 2 | PASS |
| R3 | Вебхук `paid` до создания заказа, затем создание заказа | заказ доходит до `delivered` | 2 | PASS |
| R4 | `paid` и `failed` вперемешку параллельно | итог `delivered`, `failed` после `paid` игнорируется | 2 | PASS |
| R5 | 30 параллельных `POST /api/orders` с одним `order_id` | 1 заказ в БД | 2 | PASS |
| R5b | 10 параллельных созданий и 10 `paid` по одному заказу одновременно | 1 заказ, 1 выдача | 2 | PASS |
| R6 | Пустой пул у A и B → пополнение → 10 параллельных reissue | `out_of_stock` без падения, после пополнения ровно 1 ключ, повторный reissue после выдачи `409` | 3 | PASS |
| R7 | Поставщик A выдал ключ, но ответ завис дольше таймаута | повтор с тем же `request_id` возвращает тот же код, `attempts = 2`, списан 1 | 3 | PASS |
| R7b | Поставщик A отвечает 5xx | выдача через B, у A ничего не списано | 3 | PASS |
| RS | 30 заказов при A (5xx 0.5, таймаут 0.3) и B (5xx 0.3), затем reissue восстановимых | все 30 `delivered`, 30 разных ключей, списано ровно 30, ни одного заказа с двумя выдачами | 3 | PASS |
| R8 | 50 параллельных заказов с промокодом на 3 использования | ровно 3 применены со скидкой, посчитанной сервером, остальные `409 promo_exhausted` | 4 | PASS |
| R9 | 50 параллельных заказов с кодом на 1 использование | ровно 1 применён | 4 | PASS |
| R9b | Заказ с кодом на 1 использование, оплата не прошла, повторный `failed`, новый заказ | использование возвращено ровно один раз, новый заказ берёт код | 4 | PASS |

## Как запустить

- Против живого стенда: `npm run dev`, затем `npm run race` (или `RACE_REPEAT=10 npm run race`). Один круг тратит около 40 ключей, поэтому перед каждым кругом скрипт сам пополняет пулы поставщиков через `/restock`. Скрипт печатает по строке на сценарий и итоговый инвариант: у поставщиков A и B списано ровно столько ключей, сколько заказов доведено до `delivered`.
- В процессе теста без стенда: `npm test`. Файлы `backend/test/races.test.js` и `backend/test/supplier-failures.test.js` поднимают API с БД в памяти и заглушку поставщика на случайных портах.
- В CI оба варианта: `node --test` и `race.mjs` против `docker compose`.
