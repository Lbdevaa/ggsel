# Ключевые решения

Формат: решение, почему, что отклонили. Заполняется по ходу этапов, итоговая версия попадает в README.

## D1. Хранилище: встроенный `node:sqlite`, WAL

- **Почему:** `DatabaseSync` выполняет запросы синхронно, поэтому транзакция внутри процесса не перемежается с другой: конкурентные записи сериализуются без внешних блокировок. Ноль зависимостей и нативных сборок, запуск одной командой.
- **Отклонено:** `better-sqlite3` (та же модель, но нативный модуль, под Node 26 требует сборки), Postgres в Docker (лишняя инфраструктура для MVP; при желании ту же логику даёт `FOR UPDATE SKIP LOCKED`), состояние в памяти (не переживает рестарт, не даёт гарантий).
- **Ограничение:** один процесс API. Горизонтальное масштабирование потребовало бы Postgres, логика CAS-переходов при этом не меняется.

## D2. `order_id` генерирует клиент

- **Почему:** один механизм закрывает двойной клик «Купить» (повторный POST с тем же id возвращает тот же заказ) и сценарий «вебхук пришёл раньше заказа» (событие ждёт заказ по id).
- **Отклонено:** серверный автоинкремент + отдельный Idempotency-Key (два механизма вместо одного).

## D3. Переходы статусов только через compare-and-set

- `UPDATE orders SET status=? WHERE id=? AND status IN (...)`, `changes() === 1` означает победу в гонке. Побочные действия (постановка на выдачу) выполняет только победитель.

## D4. Таймаут поставщика не равен отказу

- `request_id` детерминированный и записан в заказ до вызова. После таймаута повтор идёт с тем же `request_id` к тому же поставщику. Смена поставщика только после явного отказа.

## D5. Очередь выдачи в таблице БД, а не в памяти

- Переживает рестарт, воркер берёт задачу через CAS, `order_id UNIQUE` исключает две задачи на один заказ.

## D6. Поставщики как отдельные процессы с честной ловушкой таймаута

- Заглушка при «зависании» сначала резервирует ключ за `request_id`, потом задерживает ответ. Так воспроизводится реальный сценарий из контракта: поставщик выдал, ответ не дошёл. Повтор с тем же `request_id` возвращает тот же код даже при включённом хаосе.
- Доля 5xx и зависаний меняется на лету через `POST /chaos`, чтобы race-скрипт включал сбои точечно, без перезапуска.

## D7. Привязка заказа к поставщику вместо «контрольного запроса»

- **Проблема:** заказ упал по таймауту у B после явного отказа A. При повторной выдаче начать снова с A значит рискнуть вторым ключом: B мог выдать, ответ просто не дошёл.
- **Решение:** `orders.supplier` пишется до вызова поставщика и очищается только после его явного отказа. Повторная выдача начинает с привязанного поставщика с тем же `request_id`; по контракту он вернёт уже выданный код. К следующему поставщику переходим только после явного 4xx/5xx.
- **Отклонено:** отдельный «контрольный запрос» перед сменой поставщика. В контракте нет операции чтения, только `/issue`, и он же идемпотентен, так что контрольный запрос равен обычному повтору.

## D8. Повторная выдача только вручную

- Бриф допускает ручную или фоновую повторную выдачу. Сделана ручная через админку: оператор видит причину (`last_error`) и решает, пополнять ли остаток. Фоновый ретрай легко добавить тем же `enqueueOrRequeue` по таймеру, но без лимита попыток он бы бесконечно долбил поставщика без остатка.
